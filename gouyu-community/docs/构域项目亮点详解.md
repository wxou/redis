# 构域项目亮点详解

## 1. 使用说明与真实性口径

本文面向 Java 后端校招或实习简历，所有结果均以当前仓库实现、项目总结和联调报告为依据。

- 不使用日活、QPS、并发量、数据库降压比例等缺少压测报告支撑的数据。
- “联调通过”表示对应业务链路在真实 MySQL、Redis、Spring Boot 和 Nginx 环境中完成验证，不等同于生产环境容量证明。
- 设计收益与实测结果分开描述。例如，Stream 具备异步削峰能力，但当前项目没有可用于量化吞吐提升的基准测试。
- 商户详情当前启用缓存空值防穿透，没有将已实现但未启用的逻辑过期方案写成项目成果。
- 当前没有 Outbox 或跨 MySQL/Redis 的强一致事务；权益链路已实现有限重试、死信 Stream 与应用层补偿，但不把它描述为强一致。

## 2. 四条简历文案

以下字数包含正文中的标点、空格和英文字符，不包含列表标记。

1. 针对限时权益超卖与异步丢单，以 Lua 原子预扣并投递 Stream，结合跨消费者接管、有限重试、幂等补偿与数据库约束完成可靠落库。
2. 针对登录滥用与会话失控，实现 BCrypt 密码与验证码双登录、Redis Lua 限流、失败锁定、双重 TTL 及脱敏审计，完善认证防线。
3. 针对关注流分页易重复遗漏及作者 N+1 查询，采用 ZSet 写扩散、时间戳游标分页与批量回填作者，避免翻页错乱并消除主要 N+1 查询。
4. 针对附近商户实时距离计算与缓存失效，采用 Redis GEO 排序、MySQL 批量补全，并在商户写入时同步 GEO、删除详情缓存，降低脏数据风险。

## 3. 亮点一：高并发权益领取

### 3.1 STAR 拆解

| 要素 | 内容 |
| --- | --- |
| S（情境） | 限时权益领取包含查库存、校验重复领取、扣库存和创建订单，多请求并发执行时容易发生竞态、超卖或重复下单。 |
| T（任务） | 将入口决策原子化，把数据库写入移出请求链路，并保证锁竞争、宕机重投和业务失败不会误确认消息或永久占用资格。 |
| A（行动） | 使用 Lua 原子完成时间窗、库存、资格、状态和 `XADD`；消费者以显式处理结果决定 ACK，通过 `XPENDING + XCLAIM` 接管失联消费者消息，有限重试后写死信，并在确认 MySQL 未落单时用补偿 Lua 原子恢复库存和资格。 |
| R（结果） | 形成 `PENDING/PROCESSING/RETRYING/SUCCESS/FAILED` 可查询状态；成功消息确认后从主 Stream 删除，失败消息可补偿并在 MySQL 处理表保留归档，不再因单条毒消息无限阻塞。 |

### 3.2 核心实现流程

```text
领取请求
  -> 生成分布式订单 ID
  -> Lua 原子校验时间窗、库存与领取资格
  -> Redis 预扣库存、记录请求归属、写 PENDING、XADD 消息
  -> Stream 消费组异步消费
  -> Redisson“成员 + 权益”锁
  -> TransactionTemplate 执行数据库事务
  -> 条件扣减库存、写入订单和处理归档
  -> 成功：Lua 写 SUCCESS、XACK、XDEL
  -> 可重试失败：保留 Pending，由 XPENDING + XCLAIM 接管
  -> 超过上限：写死信；确认未落单后补偿库存和资格
  -> 客户端轮询状态 DTO
```

Lua 将“检查”和“修改”放在一次原子执行中，避免应用先读 Redis、再分多条命令更新时产生并发窗口。数据库侧继续使用 `(member_id, benefit_id)` 联合唯一约束与 `stock > 0` 条件更新，使 Redis 前置校验失效时仍有最终防线。

### 3.3 为什么选择这些技术

- **Lua**：库存、重复领取和消息投递之间存在顺序依赖，Lua 能让多步 Redis 操作原子执行，且不需要应用层分布式事务。
- **Redis Stream**：项目已经依赖 Redis，Stream 提供持久化消息、消费组、ACK 和 Pending List；配合 `XCLAIM` 与死信 Stream，可在不增加新中间件的前提下完成可恢复异步落库。
- **Redisson**：为同一成员的订单处理提供现成的分布式互斥、可重入能力和锁续期机制，降低手写锁的正确性风险。
- **数据库约束与条件更新**：Redis 适合前置拦截和快速判断，但订单与库存的事实记录仍在 MySQL，必须用数据库规则兜底。

### 3.4 与其他方案的比较

| 方案 | 优势 | 不足 | 当前选择原因 |
| --- | --- | --- | --- |
| 请求直接写 MySQL并加锁 | 事务边界清晰，数据以数据库为准 | 热点库存行容易成为瓶颈，请求需要同步等待 | 不适合把所有并发压力直接交给数据库 |
| 应用层多条 Redis 命令 | 实现直观 | 检查、扣减和投递之间存在竞态或部分成功 | Lua 能把关键步骤合并为原子操作 |
| RabbitMQ/Kafka | 消息治理、监控和扩展能力更成熟 | 增加部署、运维和学习成本 | 当前项目规模下 Stream 能复用既有 Redis |
| 仅依赖 Redis 去重 | 请求路径快 | Redis 数据丢失或重建错误时可能失去约束 | MySQL 唯一约束与条件扣减提供最终兜底 |

### 3.5 已解决的问题

- 避免库存检查和扣减分离造成的并发超卖窗口。
- 避免同一成员重复领取同一权益。
- 将数据库事务移出请求主链路，缩短请求等待范围。
- 锁竞争和暂时性数据库异常不 ACK，失联消费者的 Pending 可被其他实例接管。
- 有限重试隔离毒消息；成功或死信迁移后删除主 Stream 条目，历史写入 MySQL 处理表。
- 业务终态失败在确认订单未落库后原子回补 Redis 库存、资格和请求归属。
- 通过状态 DTO 区分处理中、重试中、成功和失败，前端不再把“暂未查到订单”当成模糊结果。

### 3.6 当前问题与改进方向

- Redis 与 MySQL 仍不是同一事务；当前依靠消息重试、订单存在性确认和幂等补偿收敛，极端故障下仍需定时对账。
- 没有 Outbox；若未来要求“数据库受理事实绝不丢失”，可改为 MySQL 受理表 + Outbox/CDC，但会增加链路和运维复杂度。
- 死信目前仍保存在同一 Redis 实例，缺少指标、告警、人工重放后台和独立持久化消息中间件。
- 单线程消费者实现简单，但吞吐能力有限；扩展消费者前需要重新评估锁粒度、消息顺序和幂等策略。
- 请求重试尚未引入客户端幂等键；客户端丢失首次成功响应时，只能得到“重复领取”，不能直接取回原订单 ID。
- 当前结果证明的是功能正确性，不代表已经完成高并发容量压测。

## 4. 亮点二：认证与安全体系

### 4.1 STAR 拆解

| 要素 | 内容 |
| --- | --- |
| S（情境） | 原有登录链路需要同时支持验证码和密码，并处理验证码滥发、登录爆破、会话无限续期、未授权写操作以及敏感审计信息泄露等风险。 |
| T（任务） | 建立覆盖凭证、请求频率、账号失败、会话生命周期、写接口鉴权和安全审计的完整认证防线。 |
| A（行动） | 实现 BCrypt 密码与验证码双登录；使用 Redis Lua 原子执行多维限流和失败锁定；设置 120 分钟空闲滑动期限与 7 天绝对期限；为写接口补充鉴权，并将脱敏手机号和 Token SHA-256 摘要写入审计表。 |
| R（结果） | 18 项认证安全断言全部通过，BCrypt、错误密码等 3 项密码测试全部通过；联调覆盖 HTTP 429、失败锁定、会话期限、密码设置/登录/修改/重置、审计落库和未登录写请求拦截。 |

### 4.2 核心实现流程

```text
登录请求
  -> Lua 校验 IP/账号频率与账号锁定状态
  -> 校验验证码或 BCrypt 密码
  -> 记录成功/失败审计事件
  -> Redis Hash 创建会话并记录签发时间
  -> 请求拦截器加载成员上下文
  -> 同时检查空闲 TTL 与绝对期限
  -> 写接口鉴权
  -> 请求结束清理 ThreadLocal
```

验证码发送限制覆盖手机号冷却、手机号每日次数和 IP 小时次数；登录限制覆盖 IP 时间窗口和单账号失败次数。多项判断及过期时间通过 Lua 一次执行，避免并发请求绕过计数上限。

### 4.3 为什么选择这些技术

- **BCrypt**：自带随机盐并可配置计算成本，适合保存用户密码，能够提高离线破解成本。
- **Redis Lua 限流**：限流状态具有短生命周期且访问频繁，Redis 适合保存计数；Lua 可保证读取、递增和设置过期时间的原子性。
- **Redis 服务端会话**：便于立即登出、失效 Token、滑动续期和调整 TTL，适合需要主动控制会话的系统。
- **双重 TTL**：滑动期限改善正常使用体验，绝对期限阻止活跃会话永久续期。
- **持久化审计表**：安全事件需要跨缓存重启保留，MySQL 比 Redis 更适合作为审计事实来源。

### 4.4 与其他方案的比较

| 方案 | 优势 | 不足 | 当前选择原因 |
| --- | --- | --- | --- |
| 仅使用 JWT | 服务端无会话查询，横向扩展简单 | 主动注销、提前失效和滑动续期更复杂 | Redis 会话更符合当前可控失效需求 |
| Java 内存限流 | 无网络访问，接入简单 | 多实例计数不共享，重启后状态丢失 | Redis 可以统一多个实例的限流状态 |
| 多条 Redis 命令限流 | 容易理解和调试 | 并发时计数与过期设置可能不一致 | Lua 保证检查、更新和 TTL 原子完成 |
| 只记录应用日志 | 开发成本低 | 查询、留存和结构化分析能力有限 | 审计表便于按事件类型、成员和时间检索 |

### 4.5 已解决的问题

- 提供验证码与密码两种互斥登录方式，并覆盖密码设置、修改和重置流程。
- 限制验证码滥发、IP 高频登录和单账号连续失败。
- 使用失败锁定降低密码爆破风险。
- 避免会话因持续访问而永久有效。
- 阻止未登录用户调用商户、权益和上传等写接口。
- 审计记录只保存脱敏手机号和 Token 摘要，减少敏感信息直接落库。

### 4.6 当前问题与改进方向

- 尚未接入真实短信服务；开发验证码回显必须在生产环境关闭。
- 当前只有登录态和写接口保护，没有管理员、商户、运营等细粒度角色权限。
- 审计范围主要覆盖认证事件，关键业务写操作审计仍需补充。
- 尚未实现设备管理、异常设备识别、全局接口限流和更完整的风险策略。
- 使用 Redis 服务端会话会增加每次鉴权的缓存访问，并需要规划 Redis 故障时的降级策略。

## 5. 亮点三：社区 Feed 与查询优化

### 5.1 STAR 拆解

| 要素 | 内容 |
| --- | --- |
| S（情境） | 关注流会持续插入新动态，传统页码分页容易在翻页时重复或遗漏；逐条查询作者还会产生列表 N+1 问题。 |
| T（任务） | 为普通社区成员设计读取快速、顺序稳定的关注流，并减少列表查询数据库的次数。 |
| A（行动） | 发布动态后把动态 ID 按时间戳写入粉丝 Feed ZSet；读取时使用最大时间戳与同分偏移量滚动分页；再批量查询动态和作者，并按 Redis 返回顺序恢复结果。 |
| R（结果） | 发布、粉丝 Feed 推送、关注流读取和滚动翻页链路完成联调；热门动态和 Feed 作者查询改为批量处理，消除了主要列表的 N+1 查询。 |

### 5.2 核心实现流程

```text
发布动态
  -> MySQL 保存动态
  -> 查询作者粉丝
  -> ZADD gy:feed:{followerId}，score=发布时间

读取关注流
  -> ZREVRANGEBYSCORE 按时间倒序取 ID
  -> 计算本页最小时间与同分偏移量
  -> MySQL 批量查询动态与作者
  -> 按 Redis ID 顺序组装结果
  -> 返回 list + minTime + offset
```

当多条动态具有相同毫秒时间戳时，仅传下一页时间戳仍可能重复读取。额外返回同分值偏移量，可以跳过已经消费的同分成员，保持滚动分页连续性。

### 5.3 为什么选择这些技术

- **ZSet**：成员唯一、分数有序，天然适合按发布时间保存 Feed 收件箱并执行倒序范围查询。
- **写扩散**：项目面向普通园区成员，单个作者粉丝量有限，发布时多写可以换取关注流读取简单且快速。
- **游标分页**：数据持续写入时，游标以已读取位置为边界，比页码加偏移量更稳定。
- **批量查询与顺序恢复**：MySQL 继续保存完整动态和作者资料，Redis 只保存排序索引；批量查询减少往返次数，再恢复 Redis 顺序保证展示正确。

### 5.4 与其他方案的比较

| 方案 | 优势 | 不足 | 当前选择原因 |
| --- | --- | --- | --- |
| 读扩散 | 发布成本低，适合大 V | 读取时需要聚合多个关注对象，延迟和计算量较高 | 普通成员粉丝规模下优先优化读取路径 |
| 写扩散 | 读取简单、顺序明确 | 发布成本随粉丝数增长 | 与当前社区用户模型匹配 |
| 页码分页 | 接口直观，可跳页 | 新数据插入后容易重复或遗漏，深分页成本高 | Feed 更适合连续滚动而不是随机跳页 |
| 逐条查询作者 | 代码直接 | 列表越长，数据库往返次数越多 | 批量查询可以消除主要 N+1 问题 |
| Elasticsearch 聚合 Feed | 检索和扩展能力强 | 引入额外索引、同步和运维成本 | 当前排序与分页需求使用 ZSet 即可完成 |

### 5.5 已解决的问题

- 关注流按发布时间倒序读取。
- 新动态持续插入时，降低翻页重复或遗漏的风险。
- 正确处理相同毫秒时间戳下的分页偏移。
- 批量加载动态作者，避免列表查询逐条访问数据库。
- 让 Redis 负责排序索引、MySQL 负责完整数据，职责边界清晰。

### 5.6 当前问题与改进方向

- 写扩散成本随粉丝数量线性增长，不适合大 V 或超大粉丝规模；可按粉丝量切换为推拉结合模式。
- MySQL 保存动态后再写多个 Feed ZSet，不是跨资源事务，失败时可能出现粉丝暂时看不到动态的情况。
- Feed ZSet 当前没有容量上限和过期清理策略，长期运行需要按时间或数量裁剪。
- 发布时间使用毫秒分值，同一毫秒仍需依靠偏移量处理；若需要严格全序，可引入复合游标或单调序列。
- 当前已优化主要作者查询，但仍应通过指标持续观察慢查询和大集合操作。

## 6. 亮点四：GEO 检索与缓存一致性

### 6.1 STAR 拆解

| 要素 | 内容 |
| --- | --- |
| S（情境） | 附近商户需要按实时距离排序，直接在 MySQL 中计算距离成本较高；商户更新后还可能出现详情缓存或 GEO 坐标仍为旧值的问题。 |
| T（任务） | 让 Redis 承担地理位置筛选与排序，同时保持 MySQL 详情、缓存和 GEO 索引在商户写入后的可用一致性。 |
| A（行动） | 按分类把商户坐标写入 Redis GEO，在五公里范围内取得 ID 和距离；使用 MySQL `IN` 批量查询详情并恢复距离顺序；商户新增或更新时同步 GEO，并删除详情缓存。 |
| R（结果） | 联调覆盖普通分类分页、GEO 距离分页、详情缓存、商户新增与更新以及 GEO 同步，相关链路全部通过。 |

### 6.2 核心实现流程

```text
附近查询
  -> 按分类查询 Redis GEO，半径 5 公里
  -> 取得商户 ID、距离及距离顺序
  -> MySQL IN 批量查询商户详情
  -> 按 Redis ID 顺序恢复结果并返回距离

商户写入
  -> MySQL 新增或更新商户
  -> 将坐标写入对应分类 GEO
  -> 更新时清理旧分类 GEO 成员
  -> 删除商户详情缓存
  -> 下一次读取回源并重建缓存
```

该设计让 Redis 保存适合地理查询和排序的轻量索引，MySQL 保存完整商户事实数据。查询结果不能直接依赖 `IN` 返回顺序，因此需要按 GEO 返回的 ID 顺序重新组装。

### 6.3 为什么选择这些技术

- **Redis GEO**：提供按半径查询、距离计算和排序能力，适合基于经纬度的附近检索。
- **MySQL 批量补全**：商户详情字段多且需要持久化，由 MySQL 统一维护，避免在 GEO 中复制完整对象。
- **Cache Aside**：写入后删除缓存，让下一次读取从数据库获取最新值，逻辑简单且避免直接更新缓存时漏字段。
- **缓存空值**：不存在的商户短时间保存空结果，降低重复无效请求穿透到数据库的概率。

### 6.4 与其他方案的比较

| 方案 | 优势 | 不足 | 当前选择原因 |
| --- | --- | --- | --- |
| MySQL 实时距离计算 | 数据源单一，无索引同步问题 | 距离计算和排序会增加数据库压力，普通索引难以直接满足 | Redis GEO 更适合作为附近查询索引 |
| Elasticsearch Geo | 查询、过滤和扩展能力强 | 增加索引同步、部署和运维复杂度 | 当前只需分类、半径和距离排序，GEO 足够 |
| 缓存与数据库同时更新 | 读取可立即命中新值 | 需要维护两份对象，字段遗漏和并发覆盖风险更高 | Cache Aside 删除策略更简单 |
| 只从 Redis 返回完整商户 | 读取路径短 | 对象更新复杂，Redis 内存占用和一致性成本提高 | GEO 只存索引，详情仍以 MySQL 为准 |

### 6.5 已解决的问题

- 避免每次附近查询都在 MySQL 中实时计算和排序距离。
- 支持按商户分类、五公里半径和距离顺序分页展示。
- 批量补全商户详情，并保持 GEO 返回的距离顺序。
- 商户新增和更新后同步地理索引。
- 更新商户后删除旧详情缓存，避免持续返回旧数据。
- 对不存在的商户缓存空值，降低缓存穿透风险。

### 6.6 当前问题与改进方向

- MySQL 提交、GEO 更新和缓存删除跨越两种存储，没有 Outbox 或消息补偿，异常时仍可能短暂不一致。
- Redis GEO 丢失后缺少完整的自动重建与校验任务，需要补充从 MySQL 重放坐标的脚本。
- 商户详情当前只启用缓存空值方案，已实现的逻辑过期代码没有启用，不能宣称已经解决热点 Key 重建问题。
- Cache Aside 仍可能在并发读写时出现旧值短暂回填，需要根据生产一致性要求选择延迟双删、版本号或消息失效方案。
- 若未来需要复杂筛选、全文检索或更大地理数据规模，应重新评估 Elasticsearch、空间数据库或专用地理服务。

## 7. 面试表达建议

### 7.1 建议的讲述顺序

1. 先说明业务问题，不要直接罗列 Redis 数据结构。
2. 再解释为什么该访问模式适合 Lua、Stream、ZSet 或 GEO。
3. 说明 MySQL 与 Redis 各自保存什么，谁是事实来源。
4. 给出联调证据，明确这些结果不是压测结论。
5. 主动补充当前方案边界以及生产化改进方向。

### 7.2 应避免的表述

- “系统支持几千并发”——当前没有可信的并发压测报告。
- “数据库压力下降百分之多少”——当前没有可对比的监控数据。
- “实现了多级缓存”——当前实际启用的是商户详情缓存空值方案。
- “保证 Redis 与 MySQL 强一致”——当前跨存储更新仍存在失败窗口。
- “Stream 等同于专业消息队列”——当前虽有有限重试、死信和补偿，但仍缺少成熟监控、独立故障域与人工重放治理。
- “Feed 适合所有用户规模”——写扩散只适合普通成员粉丝量有限的场景。
