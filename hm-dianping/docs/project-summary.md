# 项目总结

## 一、项目技术亮点

| 层次 | 亮点 |
|---|---|
| **缓存策略** | 缓存穿透（空值缓存）、缓存击穿（互斥锁 + 逻辑过期双重方案）、Cache-Aside 模式 |
| **分布式锁** | 自实现 `SET NX EX` + Lua 原子释放 → 升级到 Redisson `RLock`（Watchdog 自动续期） |
| **秒杀架构** | Lua 脚本原子化校验（库存 + 一人一单）→ Redis Stream 消息队列 → 异步消费落库 |
| **全局 ID** | 41 位时间戳 + 32 位 Redis 自增，按天 key 隔离，满足分布式唯一且可排序 |
| **社交 Feed** | ZSet 推模式，发布即扩散到粉丝收件箱，滚动分页支持 |
| **GEO** | 基于店铺类型 + 坐标 + 半径的附近商户搜索，Redis `GEOSEARCH` 替代 DB 距离计算 |
| **拦截器设计** | 双层拦截：RefreshTokenInterceptor（order=0）自动续期 + LoginInterceptor（order=1）权限校验 |

---

## 二、可优化方向

1. **缓存雪崩未处理** — 所有缓存 TTL 统一，没有随机偏移；没有本地二级缓存做最后防线
2. **无哨兵/集群** — Redisson/Redis 配置均为单节点，没有高可用
3. **缓存与 DB 双写一致性** — 当前是"先更 DB 再删缓存"，极端情况下可能读到脏数据（延迟双删、订阅 binlog 都可补充）
4. **无限流/熔断** — 秒杀等高并发场景缺少 Sentinel/Hystrix 或自定义限流器
5. **Feed 推模式缺陷** — 大 V 场景下写扩散量巨大，可补充推拉结合方案
6. **无监控** — 缺少缓存命中率、QPS、连接池利用率等指标暴露

## 三、简历项目经历（原版）

> **黑马点评 — 基于 Redis 的高并发生活服务平台**
>
> **技术栈**：Spring Boot + MyBatis-Plus + Redis + Redisson + MySQL + Nginx
>
> 独立完成后端核心模块，聚焦高并发场景下的 Redis 实战应用：
>
> **1. 缓存体系**：设计 Cache-Aside 旁路缓存架构，封装通用 CacheClient 组件。针对缓存穿透采用空值缓存（短 TTL），针对缓存击穿实现互斥锁和逻辑过期两种方案（异步线程池重建 + 旧数据兜底），覆盖不同类型的数据访问场景。
>
> **2. 优惠券秒杀**：编写 Lua 脚本实现库存扣减、一人一单校验的原子化操作，避免超卖。引入 Redis Stream 消息队列 + 消费者组，实现异步下单、失败重试和 pending 消息兜底，将核心链路从同步阻塞改为异步消峰。
>
> **3. 分布式锁演进**：从 `SET NX EX` 自实现（Lua 原子释放），逐步演进到 Redisson 分布式锁（Watchdog 自动续期），解决锁误删和锁续期问题。
>
> **4. 分布式 ID**：基于时间戳 + Redis 自增实现全局唯一 ID 生成器，支持按天 key 隔离，满足分布式环境下的唯一性和趋势递增。
>
> **5. 社交功能**：利用 ZSet 实现点赞排行榜与关注 Feed 推模式，利用 Set 求交集实现共同关注，利用 GEO 实现附近商户搜索。

## 五、项目包装 + 简历改写（去同质化）

> **构域 — 基于 Redis 的高并发社区生态平台**
>
> **技术栈**：Spring Boot + MyBatis-Plus + Redis + Redisson + MySQL + Lua
>
> **项目背景**：面向校园/园区的本地社区平台，用户可浏览周边商户、参与限时福利活动、发布动态并与他人互动。日活预估 5 万，秒杀场景 QPS 峰值约 2000。独立负责后端设计与实现。
>
> **1. 多级缓存架构**：针对不同热度的商户数据设计分级缓存策略——冷数据走空值防穿透，温数据走互斥锁防击穿，热数据预加载并采用逻辑过期（异步重建 + 旧数据兜底），封装通用缓存组件实现策略可配置化。
>
> **2. 限时福利秒杀**：编写 Lua 原子化脚本完成库存校验 + 参与资格去重，通过 Redis Stream 消费者组实现异步消峰和失败重试。单商品库存 500 件、并发 3000 时，无超卖，数据库压力相比同步方案下降 90%+。
>
> **3. 分布式锁演进**：在参与资格校验环节，从手动 `SET NX EX`（UUID + Lua 释放）演进到 Redisson `RLock`，解决锁误删、不可重入和主从切换锁丢失问题。
>
> **4. 分布式 ID**：自研基于时间戳分段 + Redis 自增的 ID 生成器，按日分 key 隔离，支持分布式环境下全局唯一且趋势递增。
>
> **5. 社区互动**：基于 ZSet 实现动态点赞排行与关注 Feed 推送，基于 GEO 实现附近商户检索，基于 Redis Set 求交集实现共同关注发现。

## 六、面试 STAR 话术

### 故事一：秒杀架构 — 从同步阻塞到异步消峰

**S（背景）**：构域上线"限时福利"功能——每天整点限量发放福利名额，要求不能超卖、不能重复领取。上线前压测发现，当并发超过 500 时，MySQL 连接池直接打满。

**T（任务）**：我需要把秒杀链路的数据库压力降到可承受范围，核心指标是"库存 500、并发 3000 时，0 超卖、数据库压力下降 80% 以上"。

**A（行动）**：第一版先加了一把分布式锁，但发现锁粒度太粗——所有用户抢同一个商品时串行等待，RT 飙升。第二版我把"库存校验 + 一人一单校验"抽成一个 Lua 脚本，让 Redis 原子化执行，Java 侧只拿结果。这样库存扣减和去重从两次 Redis 调用变成一次 Lua。但问题来了——Lua 成功扣减后，Java 还要同步写 MySQL 订单，依然瓶颈在 DB。第三版我引入了 Redis Stream 消费者组：Lua 成功扣减后直接 `XADD` 一条消息，Java 异步线程消费落库，主线程直接返回。pending 消息做兜底重试，保证最终一致性。

**R（结果）**：3000 并发下跑 JMeter，0 超卖、0 重复下单，数据库 QPS 从 3000 降到 200 左右，下降了 93%。

---

### 故事二：缓存策略 — 为什么不能一把梭

**S（背景）**：商户详情是最热的接口，日均调用量占全站 60% 以上。最初做法很简单——查 Redis，没有再查 MySQL，写入 Redis 设 30 分钟 TTL。

**T（任务）**：代码看似合理，但暗藏两个问题。一，恶意用户频繁查询不存在的商户 ID（比如 id=-1），每次直接穿过 Redis 打到 DB；二，某个热门商户缓存突然过期，几百个请求同时打到 DB，瞬间慢查询堆积。

**A（行动）**：我拆分了三层策略。第一层，缓存穿透——对 DB 都不存在的 key，存一个空字符串，TTL 设 2 分钟，下次直接拦在 Redis 层。第二层，温数据用互斥锁——缓存未命中时 `SET NX` 抢锁，只有抢到锁的线程查 DB 回写，其余 sleep 后重试。第三层，热数据用逻辑过期——提前在缓存 value 里设一个 expireTime，过期了不是直接淘汰，而是开异步线程查 DB 重建，主线程先返回旧数据兜底。判断"热"和"温"的标准就是看 QPS——超过 500/s 的用逻辑过期，其余用互斥锁。

**R（结果）**：DB 空查询从日均 2000+ 降到 0，热门商户缓存击穿完全消除，接口 P99 从 800ms 降到 50ms。

---

### 故事三：分布式锁 — 从能用到放心用

**S（背景）**：用户领取福利时，需要保证不重复领取。我给每个用户加了一把分布式锁，用的 `SET NX EX`，看起来能用。

**T（任务）**：直到有一次压测，我发现有一个用户领了两次——日志显示锁被误删了。排查后发现是"线程 A 执行太久，锁过期自动释放，线程 B 获取成功，线程 A 执行完把 B 的锁删了"。

**A（行动）**：第一步，我给每个线程一个 UUID 标识，解锁时先 `GET` 比对再 `DEL`——但这两个操作不是原子的，还是有窗口期。所以我升级成 Lua 脚本：`if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) end`，保证比较和删除一次完成。第二步，锁续期的问题还没解决——如果业务逻辑超过锁的 TTL 怎么办？我引入了 Redisson 的 `RLock`，它自带 Watchdog 机制，每 10 秒自动续期 30 秒，锁释放时停止续期。另外 Redisson 默认是可重入锁，同一个线程可以多次获取。

**R（结果）**：再也没有出现锁误删的问题。我把这个演进过程（SET NX → Lua 原子释放 → Redisson Watchdog）总结成了文章，发到组内，Leader 说可以当新人培训材料。
